Python profiler benchmark report — remote VM

The CTimer overrun fix restores Signal aggregate CPU weight to 99.58–99.63% of
observed worker lifecycle CPU, compared with 88.43–88.47% in the earlier VM run.
Under load, mean CPU cost per request was 5.25% above baseline for py-spy,
0.48% for Stack, and 1.02% for Signal/CTimer. Stack had the lowest loaded RSS
among the profilers; Signal/CTimer had the lowest idle CPU use and idle RSS.

Scope: remote VM measurements only. Main results use the fixed SDK. The
before/after section is a separate comparison with the earlier, matching VM
configuration. Smoke tests and diagnostic experiments are excluded from the
benchmark statistics. Correct aggregate CPU weight does not establish correct
stack attribution; the known attribution bias is outside this fix.

Cases run sequentially, shuffled within each repetition using seed 20261109.

Uploaded CPU weight under load

These totals cover the complete profiler lifetime, including startup, warmup
and shutdown; they must not be compared directly with only the 30-second
measurement-window CPU totals above.

For each worker, resource.getrusage(RUSAGE_SELF) was recorded around configure
and shutdown. Summed lifecycle bounds are:
  lower = CPU before shutdown - CPU after configure
  upper = CPU after shutdown - CPU before configure
The reported ratio range is uploaded weight / upper through uploaded weight / lower.

Profiler          Uploaded CPU s   Observed worker CPU bounds s   Weight / worker CPU
py-spy                  177.460         217.850–217.966          81.42–81.46%
Stack                   208.578         210.803–210.921          98.89–98.94%
Signal / CTimer         209.370         210.139–210.249          99.58–99.63%

The denominator includes every worker thread, while engines may exclude some
native threads or apply sampling filters. These ratios compare accounting;
they are not universal measures of profile accuracy.

Signal CTimer before and after the fix on the VM

Both suites used six workers, six CPUs, gil_only=False and Signal CTimer.
Main benchmark tables above contain only the fixed-SDK runs.

Version          Uploaded CPU s   Observed worker CPU bounds s   Weight / worker CPU
Before: f6a0e3e         186.150         210.406–210.517          88.43–88.47%
After: 3638f62          209.370         210.139–210.249          99.58–99.63%

Signal aggregate weight increased from about 88.4% to about 99.6% of worker
CPU. The patch preserves overrun weights; it does not repair the previously
demonstrated stack-attribution bias or the existing shutdown ordering.
This suite did not retest the controlled phase-attribution experiment.

Validation and limitations

- All 24 measurements passed; 3,766,920 successful measured requests.
- Zero measured-window HTTP errors, detected Rust panics, worker replacements
  or unclean process exits. All 18 profiled cases produced nonempty profiles.
- CPU quota, CPU affinity, six workers, profiler settings, workload hash and
  the fixed native SDK binary were verified for every case.
- No CPU quota throttling was recorded.
- A local HTTP sink acknowledged and saved uploads. Profile encoding and
  transmission remained enabled; backend ingestion costs were not measured.
- Six pinned guest CPUs do not guarantee six exclusive physical cores.
  The results apply to this workload, VM and runtime configuration.
- Sampling mechanisms differ. Lower overhead does not establish equivalent
  stack coverage or attribution accuracy.
