Finding
CTimer's scheduling-runtime clock is accurate, but Linux only checks these CPU
timer expirations on scheduler ticks while the target thread is current. Short
CPU bursts separated by blocking can avoid those checks. The timer then fires
several CPU periods late. Linux reports the missed periods in si_overrun, but
signal_sampler.rs ignores siginfo and assigns just one 10ms sample per callback.

This is established for the VM by native reproductions, SDK callback accounting,
and kernel probes. It is not a generic pending-signal explanation: the traced
Django timers were already late at cpu_timer_fire, before signal generation.
All generated signals were delivered, normally within 2–4 microseconds.

Counting 1+si_overrun restores almost all sampled-thread CPU weight in Django.
It does not restore missing frames. A controlled Python workload proves severe
attribution bias: elapsed CPU from a burst can be assigned to the following busy
phase. Elapsed CPU weighting also cannot reconstruct that missing execution.

Shutdown and proposed fixes
PyroscopeAgent::stop in rust/src/pyroscope.rs first joins the reporting thread,
which emits the final snapshot; only afterward does shutdown stop the sampler.
Signal's worker drains while running and then drops timers/session, with no
explicit full drain after disarming. Records can therefore exist after the last
report. Observed gaps are3 callbacks in the primary audit,7 in the traced audit,
and5 weighted intervals in the correction run. These are small in Django but
must be treated separately from an undelivered timer tail, which can be large.

Recommended implementation direction:
1. Preserve1+si_overrun for CTimer SI_TIMER events and carry that weight through
   the captured record, every unwind/ring/resolver failure counter and encoding.
   Preserve a single unwind per event. Do not emulate the diagnostic replay loop.
   Treat non-timer SIGPROF independently; don't read an overrun field as if valid
   for arbitrary signal origins. Use sufficiently wide/saturating accounting.
2. Stop timers, quiesce callbacks, fully drain records/drop weights, and only then
   emit the final snapshot. Observe thread lifetime/timer teardown races. If full
   CPU accounting is required, measure an armed thread's final CPU delta and
   expose otherwise-unsampled time explicitly rather than silently assigning it
   to its last stack or scaling Python stacks to include unrelated native threads.
3. Elapsed thread CPU weighting is NOT required to fix the measured bulk CTimer
   deficit: kernel overruns already encode those periods. It can represent exact
   fractions/tails with appropriate lifecycle baselines, but do not combine both
   methods and double-count. Neither method fixes pre-delivery stack bias. A
   sampling source whose trigger does not depend on the target receiving scheduler
   ticks is needed if this bursty workload's attribution must be reliable.
4. Validate total weight AND complete-stack proportions. Repeat native continuous,
   bursty, masked and long-handler controls; lifecycle/callback/overrun ledgers;
   known-CPU phase tests; concurrent/short-lived threads and shutdown boundaries.
   Exercise every supported Python3.10–3.14 layout and both Linux timer modes with
   their observed full frame sequences and documented noise tolerance. The phase
   bias test above is intentionally a failure of attribution, not a passing shape
   test after the aggregate correction.
5. Keep the recovery contract intact: successful cached initialization, preserved
   SIGSEGV/SIGBUS handlers, unblocked recovery signals on sampled and resolver
   threads, direct successful memory loads without per-read syscalls, and the
   documented deferred-read lifetime/borrow assumptions. No runtime ownership
   polling, automatic handler reclamation or unwinder mask/init checks are needed.
